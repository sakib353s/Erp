# 01. DASHBOARD — Traceability

**Status: 26 of 27 DONE, 1 PARTIAL.** Single page containing exactly **25 widget containers** (Spec §28/§48-A). Items 25+26 of the raw list (Branch Comparison, Recent Activity) are merged into one composite container so both information areas survive while the count stays 25. Containers are **not** menu pages; they are rows of the `widgets` table (`container = 'dashboard'`), seeded from `database/catalog/widgets.txt` by `WidgetSeeder`, which **refuses to seed** a catalogue that does not yield the 25 containers `config('erp.dashboard.expected_widget_containers')` mandates.

**How a container is answered.** Every panel on the page — and the JSON returned by `GET /app/dashboard/widgets/{code}` — comes from one read service, `App\Domain\Dashboard\Services\DashboardMetrics`. Each container resolves to exactly one of three honest states, and there is no fourth:

| State | Meaning | Rendering |
|---|---|---|
| `ok` | A figure computed from the company's own documents | the number, its unit caption, and the drill-down link |
| `empty` | The source exists and has no rows yet | "No data yet" plus what will fill it |
| `unavailable` | The source does not exist in the system yet | states which module will fill it — never a placeholder figure |

Nothing on the dashboard estimates, extrapolates or carries a fixture. A panel with no data says so, and a panel whose module is unbuilt names the module instead of showing a zero. `expiring_products_alert` (01-21) was that example until §04-39 shipped: it now reads the batch register (expired + expiring buckets, valued from the valuation layers) and falls back to `empty` when no dated batch holds stock — no container is left claiming a figure, and none of them invents one.

**Permission model.** A container is rendered (and its endpoint answers) only when the caller holds the **view permission of the module whose documents the panel reads** — `DashboardMetrics::PERMISSIONS` is that one map. Someone who may not read invoices never sees invoice totals, even though the dashboard page itself is open to them. The page additionally respects the widget's own `widgets.permission_id` row.

## Deviations from the planned design (recorded, not hidden)

| Planned | Shipped | Why |
|---|---|---|
| `Dashboard\WidgetDataController@show` + one `GET /dashboard/widgets/<slug>` per container, `Dashboard\Widgets\{Name}Widget` query service per panel | one endpoint `GET /app/dashboard/widgets/{code}` and one read service with a method per container | 25 identical controllers and 25 wrapper classes would be ceremony around one query each; the container code is already the unique key in the database. The states above are pinned by `DashboardWidgetTest`. |
| `dashboard.widget.*` permission key per container, plus the module key | the module's own existing view key only | One visibility vocabulary. A second, dashboard-private key set would be 25 rows no screen can manage until §12 settings ships, and a container hidden by a key the roles screen cannot show is a support ticket waiting to happen. |
| `Dashboard\WidgetRegistry` class asserting the count | `WidgetSeeder` refuses a non-compliant catalogue; `DashboardWidgetTest` asserts 25 containers and that every container has a metric | The invariant is enforced at the only two moments it can break: seeding and deployment. |
| `Reporting\Aggregates\*` pre-aggregated `bi_metrics_daily` | direct bounded queries over the source documents (14-day, current-month, open-document windows) | `bi_metrics_daily` is populated by §13 reporting, which is still PLANNED. Caching a number whose invalidation rules do not exist yet would make the dashboard *less* trustworthy than reading the source. |
| `WidgetTodaysSalesTest` … 25 per-widget tests | `DashboardWidgetTest` (4) covering the contract every container shares, plus per-container assertions for the states that can be reached today | A per-container test for a panel whose source is `unavailable` would only re-assert the third state 25 times. |

One real defect was found and fixed while wiring this: `WidgetSeeder::codeFor()` produced mixed-case codes (`Todays_Sales`), while every consumer keys off lowercase slugs — the translations table (`widget.todays_sales`), the label keys and the dashboard's own metric map. Container codes are lowercase now, and the seeder prunes containers that fall outside the catalogue so an already-seeded instance ends up with one of each panel rather than two.

No PHP runtime exists in the build sandbox, so this suite is written and statically audited (route names, permissions, view contracts, catalogue-to-metric coverage) but has **not been executed** — stated here rather than implied.
