## 16.2 Warranty & QR verification (Spec §7/§8)

**Built this slice: the invoice verification link and the page behind it (§16-19, §16-20).** Then **the public document link and its secure download (§16-21, §16-22)**, which reuse that shape deliberately so the application tells one story about handing a file to somebody without a login: the address is derived from `document:{company}|{document}|{rotation}` and only its digest is stored, so a screen can show the address again while a read-only leak of the `documents` table publishes nothing; rotation is a version bump, withdrawal keeps its date **and takes the file back to `visibility = private`** — the document foundation already had its own rule (`allowsPublicAccessByToken`, which asks for a live token *and* public visibility), and the share flow now satisfies it rather than quietly contradicting it. A **permanent link is one with no expiry**; an expiry is explicit and bounded to a year, and the moment it passes the address is a 404 like any other. The download streams the stored bytes from the private disk with the file's own MIME type and a filename that cannot climb out of a directory, and views and downloads are recorded as different facts (`documents.public_link_viewed` versus `documents.public_file_downloaded`) with the token's hash in the access log. While wiring it, two real defects on the documents desk were found and fixed: the library page eager-loaded and printed a relation called `uploadedBy` that does not exist on the model (the page returned 500 for every user), and `Document` was missing the `branch()` relation its own `branch_id` column and branch scope imply. Two decisions carry it, and both are about not lying with a URL. **The token is derived and only its hash is stored.** A printed invoice carries a QR symbol and a reprint has to produce the same address, so the capability cannot be a value that lives only in the response of the request that created it: it is `HMAC-SHA256(APP_KEY, "verification:{company}|{invoice}|{rotation}")` base64url-encoded (43 characters, 32 bytes of entropy, no invoice number in sight), and what the row holds is `hash('sha256', $token)`. A read-only leak of the invoices table therefore publishes nothing, and a lookup compares against a digest rather than a capability. Rotation is a version bump — the old address 404s the instant the version moves and a reprint carries the new one — and withdrawal keeps the date it happened, so “this invoice was verifiable until 4 March” stays a fact. **The page publishes the document, not the books.** It names the company and branch that issued it, the number, the date, what was bought, what is paid and due and who raised it; the internal notes, the journal entry, the audit chain, costs and every other customer are never read rather than filtered out. Customer contact details are masked on the page, because a link can be forwarded or photographed off a counter. Warranty dates are deliberately absent: `warranty_flag` says terms were promised on the line, but warranties are not registered in this application yet (§16-16), so the page says exactly that instead of showing a date nobody recorded. Every visit writes one `public_access_logs` row — with the token's **hash** in the `access_token` column, so the log can say which link was used without publishing a capability to whoever can read a log table — and one audit event (`sales.invoice_verified`); publishing, rotating and withdrawing each audit their own action behind the key that already owns the document's life cycle (`sales.invoices.issue`). Drafts and pending invoices are refused by the service rather than only hidden in the view: a customer verifying a draft would be verifying something the company has not asked them to pay, and a cancelled invoice verifies **as** cancelled, because the point of a verification page is that it can say what the paper cannot.
