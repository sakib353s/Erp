# 04. INVENTORY — Traceability

Baseline (`BL`) applies. Core rule: **stock truth = immutable `stock_movements`**; `stock_balances` is derived and rebuildable; valuation layers per configured method (FIFO / LIFO / Weighted Average / Standard); FEFO for expiry goods; negative-stock guarded by row lock + CHECK where disabled.

Shared services: `Inventory\Actions\{CreateProduct, DuplicateProduct, CreateOpeningStock, PostStockAdjustment, CreateStockTransfer, DispatchTransfer, ReceiveTransfer, RecordDiscrepancy, PostCycleCount, RecordDamage, RecordLoss, RequestWriteOff, PostWriteOff, ConsumePackaging, GenerateBarcodeLabel, CreateReorderSuggestion}` · `Inventory\Services\{StockLedgerService, ReservationService, ValuationService(FIFO/LIFO/WAC/Standard), FefoAllocator, SerialService, BatchService, ReorderCalculator, ReconciliationService}` · `Inventory\Queries\{StockQuery, ValuationQuery, MovementQuery, ExpiryQuery}` · engines: Workflow, Accounting (`posting_rules` for write-off/adjustment/valuation), Documents, Audit, Intelligence.

> **Phase E note (rows DONE above):** sole mutation path `StockLedgerService`; balances derived/rebuildable; two-leg transfer uses `TRANSIT_OUT` (dispatch) → `TRANSIT_CLEAR` (origin) + `TRANSIT_IN` (dest) on receive; short receive opens `discrepancy`. Adjustment WF threshold + inventory GL posting and a dedicated `/inventory/valuation` UI page remain open (core stock/layer effects only). > **Phase E/§04-46…04-51 note:** two documents, because they are two different statements. A **damage/loss entry** records a fact: `damage` moves goods out of sellable stock into the damaged compartment with **no valuation effect** (still ours, same cost — `StockMovement::TYPE_DAMAGE_IN`, reversible with `TYPE_DAMAGE_RELEASE`), while `loss` consumes the layers and posts Dr 5260 / Cr 1140. A **write-off** is the decision that value leaves: raised against a compartment (`damaged`/`quarantined`/`on_hand`), approved by a *different* person, and only then does `DAMAGE_OUT`/`WRITE_OFF` move stock, consume layers and post. The ledger's state machine now lives on `StockMovement::applyDelta()` — **one definition** used by the live post path, the balance rebuild and the ledger view's running on-hand column — and it was corrected here: an outbound movement from the damaged compartment used to decrement `on_hand` a second time (goods were already taken out when they were flagged), which made disposal from that compartment impossible without corrupting sellable stock. `damaged` and `quarantined` are compartments held *outside* sellable stock and are valued all the same. Document naming deviates from the plan's `damage_loss_records`: one register with `kind`, plus a separate write-off document, because the two carry different permissions and different effects.
> **Phase F note (04-23/04-24/04-57):** alerts are judged by `ReorderService::alertRows` against `reorder_policies`; a product with no active policy is deliberately never listed, and a warehouse row beats the company-wide row. Thresholds are validated as a set (minimum ≤ reorder point ≤ maximum, safety ≤ reorder point), and a refused policy writes nothing. The alert screen links straight into a prepared purchase order (`?product=&qty=`). `StockQuery::alerts()` predates this and is **not** the screen source — it stays for the balance-only summary; the screen and every doc line point at `ReorderService`.
