# 04. INVENTORY — Traceability

Baseline (`BL`) applies. Core rule: **stock truth = immutable `stock_movements`**; `stock_balances` is derived and rebuildable; valuation layers per configured method (FIFO / LIFO / Weighted Average / Standard); FEFO for expiry goods; negative-stock guarded by row lock + CHECK where disabled.

Shared services: `Inventory\Actions\{CreateProduct, DuplicateProduct, CreateOpeningStock, PostStockAdjustment, CreateStockTransfer, DispatchTransfer, ReceiveTransfer, RecordDiscrepancy, RecordDamage, RecordLoss, RequestWriteOff, PostWriteOff, ConsumePackaging, GenerateBarcodeLabel, CreateReorderSuggestion}` (the count is a **service**, not an action — `Services\StockCountService` — because a count session spans many screens: open, count, post, cancel) · `Inventory\Services\{StockLedgerService, ReservationService, ValuationService(FIFO/LIFO/WAC/Standard), FefoAllocator, SerialService, BatchService, ReorderCalculator, ReconciliationService}` · `Inventory\Queries\{StockQuery, ValuationQuery, MovementQuery, ExpiryQuery}` · engines: Workflow, Accounting (`posting_rules` for write-off/adjustment/valuation), Documents, Audit, Intelligence.

> **Phase E note (rows DONE above):** sole mutation path `StockLedgerService`; balances derived/rebuildable; two-leg transfer uses `TRANSIT_OUT` (dispatch) → `TRANSIT_CLEAR` (origin) + `TRANSIT_IN` (dest) on receive; short receive opens `discrepancy`. The adjustment approval threshold (§04-26) is now wired — settings-driven, maker ≠ checker, pending documents carry no movements; inventory GL posting for adjustments and a dedicated `/inventory/valuation` UI page remain open (core stock/layer effects only). > **Phase E/§04-42…04-45 note:** the warehouse module is the *geography* of stock, and it deliberately does **not** store quantities per bin. `stock_balances` counts stock per product per warehouse; a second place where a number could live would be a second truth to reconcile, so a bin is where a picker is told to go and nothing more. Zones carry a purpose so a putaway or pick task has something to read later (04-44 stays PLANNED). The map is rendered from rows — including a "placed here, untouched for 60 days" list, which is the kind of thing a hand-drawn map cannot say. Zones and bins share the warehouse's own permission keys (`warehouses.view/create/update/delete`, declared in Phase 1) instead of inventing `inventory.warehouses`: the physical layout *is* the warehouse, and the plan's single `inventory.warehouses` key would have duplicated them. They also share its **surface**: warehousing lived at `/app/warehouses` before this slice, so zones, bins, assignment and the map were added to that same block rather than opening a second warehouse module beside it — one list, one form, one layout screen per warehouse, and every `inventory > warehouse > …` menu entry lands on it. A warehouse's code is unique inside its branch and may be renamed (stock rows point at the id, not the code); changing the branch it reports under is refused once it has moved stock, because stock is reported branch by branch; and a branch keeps exactly one default warehouse, so making one default demotes the other.
> **Phase E/§04-31 note:** a count sheet is a **snapshot, not a live view**: opening it freezes `system_qty` per line, because a sheet that followed the warehouse would always agree with itself. Posting then applies the difference between the balance *now* and the counted figure — not the difference against the snapshot — so the shelf ends where the counter left it; both numbers are stored (`variance` vs `posted_delta`) so stock that moved during the count stays visible instead of being smoothed away. Two deviations from the plan, both deliberate: the tables are `stock_counts`/`stock_count_lines` (the plan says `cycle_counts`, but the same document serves a full stock-take and a cycle round, and one table with a `scope` column is what the screen actually shows), and posting is gated by its own `inventory.counts.post` rather than reusing the adjustment approval key, because counting and changing the books are different jobs. A full sheet lists **every active stocked product**, including products the ledger believes are at zero — finding stock nobody expected is half the point. Counting is **blind** for anyone without `inventory.counts.post`: the expected figure is not rendered at all, not merely hidden with CSS.
> **Phase E/§04-46…04-51 note:** two documents, because they are two different statements. A **damage/loss entry** records a fact: `damage` moves goods out of sellable stock into the damaged compartment with **no valuation effect** (still ours, same cost — `StockMovement::TYPE_DAMAGE_IN`, reversible with `TYPE_DAMAGE_RELEASE`), while `loss` consumes the layers and posts Dr 5260 / Cr 1140. A **write-off** is the decision that value leaves: raised against a compartment (`damaged`/`quarantined`/`on_hand`), approved by a *different* person, and only then does `DAMAGE_OUT`/`WRITE_OFF` move stock, consume layers and post. The ledger's state machine now lives on `StockMovement::applyDelta()` — **one definition** used by the live post path, the balance rebuild and the ledger view's running on-hand column — and it was corrected here: an outbound movement from the damaged compartment used to decrement `on_hand` a second time (goods were already taken out when they were flagged), which made disposal from that compartment impossible without corrupting sellable stock. `damaged` and `quarantined` are compartments held *outside* sellable stock and are valued all the same. Document naming deviates from the plan's `damage_loss_records`: one register with `kind`, plus a separate write-off document, because the two carry different permissions and different effects.
> **Phase F note (04-23/04-24/04-57):** alerts are judged by `ReorderService::alertRows` against `reorder_policies`; a product with no active policy is deliberately never listed, and a warehouse row beats the company-wide row. Thresholds are validated as a set (minimum ≤ reorder point ≤ maximum, safety ≤ reorder point), and a refused policy writes nothing. The alert screen links straight into a prepared purchase order (`?product=&qty=`). `StockQuery::alerts()` predates this and is **not** the screen source — it stays for the balance-only summary; the screen and every doc line point at `ReorderService`.
