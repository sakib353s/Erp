# 15. SETTINGS — Traceability

Baseline (`BL`) applies. Settings engine (Spec §38): structured DB records — key, group, value, type, scope (global/company/branch), effective date, translated help text, **secret flag + encrypted storage** for credentials, full audit history. **Unsafe "everything configurable" switches forbidden**: authorization, isolation, FK integrity, debit/credit balance, decimal arithmetic, posted-record immutability, idempotency, numbering uniqueness, token entropy, password hashing, transport security are **not** toggleable (tested in 15 row S-23).

Shared: `Settings\SettingsService` (typed get/set with cache invalidation after commit), `Settings\Controllers\*`, `Security\SecurityPolicyService`, `Backup\BackupService`, `Maintenance\MaintenanceService`, `Documents\TemplateController`, `Api\ApiKeyService`, `IntegrationService`.

**Built as §15-01, 15-02, 15-03, 15-15, 15-16, 15-17 and the invariant guard (15-35):** the settings desk has a landing page (`GET /app/settings`) and one screen per group, driven from `config('erp.settings.groups')` — the group's own metadata decides the fields, the types, the limits and the default, so a settings screen never grows a field nobody can trace. Three things were added to the foundation to make the desk trustworthy rather than merely present:

  · **a key per group.** `settings.view` opens the module (`settings.<group>` opens that group's numbers) and `settings.update` is what writes. A person who may set the company's document numbering has no business rewriting the password policy, and one blanket switch had said they did. The group screen is the consumer of each key, and the desk lists every group either way — with the key it needs — so a locked group is visible rather than absent.
  · **the invariant floor** (`Setting\s\Services\InvariantGuard`, §15-35). Called from `SettingService::set()`, which is the one function every write goes through, the guard refuses three things: a value below a fixed floor (password minimum 8, lockout attempts 3, lockout minutes 1, session idle 5, audit retention 30 days, workflow due-hours 1, audit verification reminder 1h), a protected identity key (`instance.slug` and friends), and a **branch override of a policy group** — security, audit, workflow and notifications are company-wide because a weak outlet would be a weak door into the same books, a branch may not shorten the trail its own mistakes are written to, approval thresholds are a control rather than a preference, and one branch silencing an alert would silence it for the company. A refusal is a field-scoped validation error the person can act on, and it is audited as `config.invariant_denied` with the reason, so an attempt is visible even when nothing changed.
  · **branch scope** (§15-03): `GET /app/settings/branches` lists the branches with how much each has decided for itself, and `GET|POST /app/settings/branches/{branch}` shows the company's value beside the branch's for every field a branch may set. A branch outside the actor's scope is **403 with the branch named**, not a server error. Removing an override **deletes the branch row** (`SettingService::forget()`) rather than copying the company's number into it — copying would freeze that branch at today's figure and quietly stop following the company tomorrow. Both screens build their validation from `Settings\Support\GroupRules`, the same rules the company form uses, so a branch cannot become the laxer door into the same table.

Reading a group and writing one are separate keys, and **a refused write is never reported as a save**: `setGroup()` returns the keys it stored and the keys it refused, and both settings screens (and the POS screen) now report the two separately instead of counting refusals as successes.

Still PLANNED, and why: the invoice/print template family (15-06, 15-20) needs the §19 document frame; the payment-gateway, courier, SMS, SMTP, WhatsApp and Firebase groups (15-08…15-13) are real screens only when an adapter exists to talk to, and shipping an encrypted credential form with nothing behind it is the fake work this project forbids; backups and data export (15-18, 15-19) need the archive format and a restore path that can be tested; API keys (15-21) and the maintenance family (15-23…15-34) are the next slice after this one.
