# 15. SETTINGS — Traceability

Baseline (`BL`) applies. Settings engine (Spec §38): structured DB records — key, group, value, type, scope (global/company/branch), effective date, translated help text, **secret flag + encrypted storage** for credentials, full audit history. **Unsafe "everything configurable" switches forbidden**: authorization, isolation, FK integrity, debit/credit balance, decimal arithmetic, posted-record immutability, idempotency, numbering uniqueness, token entropy, password hashing, transport security are **not** toggleable (tested in 15 row S-23).

Shared: `Settings\SettingsService` (typed get/set with cache invalidation after commit), `Settings\Controllers\*`, `Security\SecurityPolicyService`, `Backup\BackupService`, `Maintenance\MaintenanceService`, `Documents\TemplateController`, `Api\ApiKeyService`, `IntegrationService`.

**Built as §15-01, 15-02, 15-03, 15-04, 15-05, 15-07, 15-15, 15-16, 15-17, the maintenance family (§15-23…§15-33) and the invariant guard (15-35):** the settings desk has a landing page (`GET /app/settings`) and one screen per group, driven from `config('erp.settings.groups')` — the group's own metadata decides the fields, the types, the limits and the default, so a settings screen never grows a field nobody can trace. Three things were added to the foundation to make the desk trustworthy rather than merely present:

  · **a key per group.** `settings.view` opens the module (`settings.<group>` opens that group's numbers) and `settings.update` is what writes. A person who may set the company's document numbering has no business rewriting the password policy, and one blanket switch had said they did. The group screen is the consumer of each key, and the desk lists every group either way — with the key it needs — so a locked group is visible rather than absent.
  · **the invariant floor** (`Setting\s\Services\InvariantGuard`, §15-35). Called from `SettingService::set()`, which is the one function every write goes through, the guard refuses three things: a value below a fixed floor (password minimum 8, lockout attempts 3, lockout minutes 1, session idle 5, audit retention 30 days, workflow due-hours 1, audit verification reminder 1h), a protected identity key (`instance.slug` and friends), and a **branch override of a policy group** — security, audit, workflow and notifications are company-wide because a weak outlet would be a weak door into the same books, a branch may not shorten the trail its own mistakes are written to, approval thresholds are a control rather than a preference, and one branch silencing an alert would silence it for the company. A refusal is a field-scoped validation error the person can act on, and it is audited as `config.invariant_denied` with the reason, so an attempt is visible even when nothing changed.
  · **branch scope** (§15-03): `GET /app/settings/branches` lists the branches with how much each has decided for itself, and `GET|POST /app/settings/branches/{branch}` shows the company's value beside the branch's for every field a branch may set. A branch outside the actor's scope is **403 with the branch named**, not a server error. Removing an override **deletes the branch row** (`SettingService::forget()`) rather than copying the company's number into it — copying would freeze that branch at today's figure and quietly stop following the company tomorrow. Both screens build their validation from `Settings\Support\GroupRules`, the same rules the company form uses, so a branch cannot become the laxer door into the same table.

Reading a group and writing one are separate keys, and **a refused write is never reported as a save**: `setGroup()` returns the keys it stored and the keys it refused, and both settings screens (and the POS screen) now report the two separately instead of counting refusals as successes.

Then the maintenance family (§15-23…§15-33), which is where this module earns the trust the rest of it asks for. Every operation on the desk is real, permission-scoped to the kind of work it does (`maintenance.cache` is not `maintenance.repair` is not `maintenance.reset`), and written to two places: a `maintenance_runs` row carrying the figures and an audit event for the chain. The rules are the design: a closed allow-list of sweeps that can never reach uploads, backups, logs or sessions; a temp sweep that skips anything younger than 24 hours and refuses to follow a symlink out of the tree; a repair that refuses without the word `REPAIR` typed, a check on file, *and* a table that check named — never automatic, and absent from self-healing entirely; a settings reset that deletes rows instead of rewriting them, so an unchosen default stays visibly unchosen. And the page says what it cannot see: single instance rather than a high-availability claim, backups “not built in this build” rather than a green tick, queue worker and scheduler “unknown from here”. The log viewer masks secrets before rendering and says how many it masked.

Then the localization switches (§15-07), which had existed as four values and nothing else. `LocalizationService` is now the one place a document asks how to print a figure: lakh/crore grouping by default (`12,34,567`, not `1,234,567` — the subcontinent reads its own grouping), বাংলা numerals when asked and applied *after* grouping so the separators land in the right places, quantities without grouping because nobody writes 1,20 items, and the amount in words taken from the number the totals were computed from rather than from a formatted string that may already have lost a paisa. The commercial invoice, the statutory Mushak 9.1 and the POS receipt all render through it, and the group's own screen shows a live sample rendered by the same service, so the sample cannot drift from the document. The language toggle is real too: `Translator::locale()` now reads the group's `default_locale` (a reader's own session choice still wins) and saving the group flushes the translator's memo, so the switch takes effect on the next render instead of the next deploy. Branch scope reaches the paper — a Narayanganj outlet may print `৳৪৫০.০০` while head office prints `৳450.00` from the same invoice. The catalogue's four Bengali leaves point at the fields they name (`#bengali_numerals`, `#amount_words_bn`, `#lakh_crore_format`), and every seeded deep link is walked by a test that looks for the id it must land on.

Still PLANNED, and why: the invoice/print template family (15-06, 15-20) needs the §19 document frame; the payment-gateway, courier, SMS, SMTP, WhatsApp and Firebase groups (15-08…15-13) are real screens only when an adapter exists to talk to, and shipping an encrypted credential form with nothing behind it is the fake work this project forbids; backups and data export (15-18, 15-19) need the archive format and a restore path that can be tested; API keys (15-21), the VAT & tax group (15-14) and the factory reset (15-34) are the remaining rows — and a factory reset cannot honestly exist before backups do.
